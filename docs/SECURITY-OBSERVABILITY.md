# Recovery evidence and security investigation

The actual platform now projects selected existing recovery receipts, terminal email outcomes and recovery-storage authorization/account-key observations into a separate hub security table. It does not forward backup payloads, keys, recipient addresses or raw console messages.

A five-minute managed-identity collector uses its own DCR and private leased checkpoint. Arrival-time windows preserve delayed records while evidence keeps its original time. Investigation counts deduplicate stable event IDs; two stored copies are not two recovery operations.

The November 14 healthy payroll-coverage cohort matched all eleven projected fields in the hub: two stored rows, one distinct ID and 718 billed row bytes. No new backup or restore was forced for this observation. Nonproduction synthetic/restart acceptance and complete temporary endpoint/settings/pause cleanup also passed. These are dated platform observations; the public local demo and its screenshots retain their fictional scope.

Collection is live; new operations-specific detection rules and notification routes are not activated. A current-coverage receipt is not a restore rehearsal. Backstage PostgreSQL helpers still lack confirmed centralized structured receipts, and key-rotation collection remains separate. Existing backup alerts and HTTP security detections have their own scope.

[The companion Sentinel project](https://github.com/truthofsource/azure-sentinel-detection-and-incident-response/blob/main/docs/OPERATIONS-COLLECTION.md) contains the source-table map, data limits, diagram, query, troubleshooting and acceptance boundaries. This repository does not provision that later collector.

**Scaling:** Measure source delay, duplicate copies, cursor lag, query duration and billed bytes before adding sources. More evidence also adds ingestion cost and review work; preserve restore validation, access controls and recovery cleanup independently.
